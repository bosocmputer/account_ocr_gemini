# สมองร้าน (Shop Brain): หลักการทำงานและการดึงข้อมูล

สมองร้านเรียนรู้ว่าแต่ละร้านลงบัญชีอย่างไร โดยดูจากรายการบัญชีที่ร้านบันทึกไว้แล้ว และ**ไม่ใช้ AI** หลักการคือ "จำว่าเคยลงบัญชีแบบไหน แล้วตอบตามนั้นเฉพาะตอนที่มั่นใจ"

- โค้ดฝั่ง backend: `internal/shopbrain` (billscan)
- หน้าจอ: `/shop-brain` ใน bcaccount

## 1. การดึงข้อมูล

เมื่อเปิดหน้า `/shop-brain` หน้าเว็บจะเรียก `GET /billscan/api/v1/shop-brain?shopid=…` จากนั้น billscan ทำตามลำดับนี้

1. **ตรวจสิทธิ์:** ส่ง token ไปถาม MAIN_API (`/list-shop`) ว่าผู้ใช้เป็น Owner ของร้านนี้ (role 2) หรือไม่ ถ้าไม่ใช่ จะไม่ได้ข้อมูล
2. **อ่านจาก Mongo หลัก (อ่านอย่างเดียว ไม่เขียนกลับ)**
   - **รายการบัญชี (journal) ทั้งหมดของร้าน** ดึงเฉพาะฟิลด์ที่ใช้: เลขที่เอกสาร, วันที่, ประเภทเอกสาร (docformat), สมุด, คำอธิบาย, บรรทัด Dr/Cr, VAT, หัก ณ ที่จ่าย และคู่ค้า
   - **กลุ่มเอกสาร (รูปภาพ):** ใช้ดูว่ารายการมีรูปบิลแนบหรือไม่ เพื่อแยกที่มาเป็น *มีรูป / ไม่มีรูป / Statement*
   - **ข้อมูลหลัก:** ผังบัญชี, เจ้าหนี้, ลูกหนี้ (รวมเลขผู้เสียภาษี), ประเภทเอกสาร, สมุดบัญชี, สมุดธนาคาร และงวดบัญชี
3. **เก็บผลไว้ในหน่วยความจำ 10 นาที:** ถ้าเปิดหน้าซ้ำภายในช่วงนี้ จะไม่ดึงข้อมูลใหม่ ถ้าต้องการคำนวณใหม่ทันที ให้กดปุ่ม "อัปเดตข้อมูลล่าสุด"

ระบบไม่อ่านรูปบิล ไม่เรียก OCR และไม่เรียก AI จึงไม่มีค่าใช้จ่ายต่อครั้ง

```
หน้า /shop-brain ──► billscan /api/v1/shop-brain
                        │ 1. ตรวจ Owner ผ่าน MAIN_API
                        │ 2. อ่าน journal + ข้อมูลหลักจาก Mongo หลัก (read-only)
                        │ 3. สร้างสมอง + จำลองย้อนหลัง (เก็บไว้ 10 นาที)
                        ▼
                    ส่งผลกลับหน้าเว็บ (แผนที่สมอง / ตรวจสมอง / ข้อมูลละเอียด)

ผลที่ผู้ใช้กดตัดสิน ──► billscan /api/v1/shop-brain/feedback ──► shopbrain-mongo (แยกจาก Mongo หลัก)
```

## 2. การเรียนรู้

### 2.1 รูปร่างการลงบัญชี
แต่ละรายการบัญชีถูกสรุปเป็น "รูปร่าง" ซึ่งประกอบด้วย

- บัญชีฝั่งเดบิตและเครดิต เช่น `เดบิต ค่าไฟ + ภาษีซื้อ / เครดิต เงินสด`
- สัดส่วนยอดของแต่ละบรรทัดเทียบกับยอดรวม
- มี VAT และหัก ณ ที่จ่ายหรือไม่

### 2.2 กุญแจ 4 ชั้น (ไล่จากเจาะจงที่สุดไปกว้างที่สุด)

| ชั้น | กุญแจ | ตัวอย่าง |
|---|---|---|
| L1 | เลขผู้เสียภาษี 13 หลัก + ประเภทเอกสาร | บิลจากเลข 0105… ลงแบบเดียวกันทุกครั้ง |
| L2 | รหัสคู่ค้า + ประเภทเอกสาร | ลูกหนี้ AR-004 → ลูกหนี้ / รายได้ขาย |
| L3 | คำอธิบายรายการ (ตัดตัวเลขและเครื่องหมายออก) + ประเภทเอกสาร | "ค่าไฟฟ้า 04/26" และ "ค่าไฟฟ้า 05/26" เป็นกุญแจเดียวกัน |
| L4 | ประเภทเอกสาร + สมุด | ใช้เป็นทางสุดท้าย เมื่อไม่มีข้อมูลอื่น |

แต่ละกุญแจจะนับไว้ว่าเคยลงบัญชีแบบไหนกี่ครั้ง และให้น้ำหนักแต่ละรายการไม่เท่ากัน

- **รายการใหม่มีน้ำหนักมากกว่ารายการเก่า:** น้ำหนักลดลงครึ่งหนึ่งทุก 180 วัน ถ้าร้านเปลี่ยนวิธีลงบัญชี สมองก็จะตามวิธีใหม่
- **รายการที่นักบัญชีติ๊กตรวจแล้ว:** น้ำหนัก × 1.5

## 3. การตอบ (ส่วนที่ควบคุมความถูกต้อง)

สมองไล่หาคำตอบจาก L1 ไปถึง L4 และเลือก**ชั้นแรกที่ผ่านเกณฑ์ทั้ง 3 ข้อ**

| เกณฑ์ | L1 | L2 / L3 | L4 |
|---|---|---|---|
| 1. เคยเห็นอย่างน้อย | 1 ครั้ง | 2 ครั้ง | 2 ครั้ง |
| 2. ความมั่นใจ (Wilson lower bound ของสัดส่วนแบบที่ใช้บ่อยที่สุด, z = 1.28) อย่างน้อย | 60% | 60% | 90% |
| 3. ครั้งล่าสุดที่ต้องลงแบบเดียวกับแบบที่ใช้บ่อยที่สุด | 2 ครั้ง | 2 ครั้ง | 2 ครั้ง |

- **เกณฑ์ข้อ 2:** ใช้ขอบล่างของความมั่นใจแทนสัดส่วนดิบ ตัวอย่างน้อยจึงต้องสม่ำเสมอมากขึ้นถึงจะผ่าน เช่น 2/2 → 55% (ไม่ผ่าน), 3/3 → 65% (ผ่าน), 17/20 → 73% (ผ่าน)
- **เกณฑ์ข้อ 3:** ช่วยจับร้านที่เปลี่ยนวิธีลงบัญชี ส่วนใหญ่เคยลงแบบ A แต่ช่วงหลังลงแบบ B สมองจะไม่ตอบ A
- **L4 ใช้เกณฑ์ 90%** เพราะเป็นชั้นที่กว้างที่สุดและเสี่ยงเดาผิดมากที่สุด
- **Statement ธนาคาร:** กุญแจทุกชั้นมี**เงินเข้า/เงินออก**ต่อท้าย ทิศทางมาจากด้าน Dr/Cr ของบัญชีธนาคารของชุดที่นำเข้า (บัญชีที่อยู่ในทุกรายการของ `batchid` เดียวกัน) ซึ่งเป็นข้อมูลที่ Statement มีอยู่แล้ว เหตุผลคือข้อความเดียวกัน เช่น "transfer" ลงบัญชีต่างกันระหว่างเงินเข้ากับเงินออก

ถ้าไม่มีชั้นไหนผ่าน **สมองจะตอบว่า "ไม่รู้" แทนการเดา** และบอกเหตุผลของแต่ละชั้นว่าไม่ผ่านเพราะ*ไม่เคยเห็น* *เห็นน้อยไป* *ยังไม่มั่นใจพอ* หรือ*ช่วงหลังลงไม่เหมือนเดิม*

### ที่มาของเกณฑ์ (ทดลองบนข้อมูลจริง 2026-11-25)

ได้จากการจำลองย้อนหลังแบบอ่านอย่างเดียว บน prod 4 ร้าน (ซันมัย, มีพร้อม, ภูพิงค์ แอร์, กินดีฟาร์ม) รวม 4,042 รายการ ด้วย `internal/shopbrain/experiment_prod_test.go`

| | เกณฑ์เดิม | เกณฑ์ใหม่ |
|---|---|---|
| บิลที่มีรูป: ถูก (ในข้อที่ตอบ) | 73–92% | 91.5–97.7% |
| บิลที่มีรูป: ตอบได้ | 46–84% | 22–69% |
| ทั้งหมด: ตอบผิด (4 ร้านรวม) | 220 ครั้ง | 44 ครั้ง |

การแยกซื้อ/ขายในชั้นเลขผู้เสียภาษีไม่มีผลกับร้านเหล่านี้ จึงไม่ได้ใช้ ข้อมูลใน dev เป็นข้อมูลทดสอบ จึงห้ามใช้ปรับเกณฑ์

## 4. แถบผล "ลงถูก / ลงผิด / ไม่รู้"

หน้าเว็บแสดงผลเป็นแถบเดียว แบ่งรายการเก่าทั้งหมดของร้านออกเป็น 3 กลุ่ม ตัวเลขมาจาก**การจำลองย้อนหลัง**

1. เรียงรายการบัญชีทั้งหมดของร้านตามเวลา
2. ให้สมองทายทีละรายการ โดยรู้เฉพาะรายการที่เกิด**ก่อนหน้า**เท่านั้น เหมือนการทายอนาคตจริง
3. เทียบคำทายกับที่บันทึกไว้จริง แล้วนับแต่ละรายการเข้ากลุ่ม

| กลุ่ม | ความหมาย | คำนวณจาก (`backtest.overall`) | สีในหน้าเว็บ |
|---|---|---|---|
| ลงถูก | บัญชีตรงกับที่นักบัญชีบันทึกไว้ | `hit_accounts` | สีหลักของ theme |
| ลงผิด | สมองตอบ แต่ไม่ตรงกับที่บันทึกไว้ ต้องให้คนแก้ | `predicted − hit_accounts` | แดงลายทาง |
| ไม่รู้ | สมองไม่มั่นใจ จึงไม่เดา ให้คนลงเองเหมือนเดิม | `total − predicted` | เทา |

ตัวอย่างร้านดูโก้ (dev, 414 รายการ, เกณฑ์เดิม): ลงถูก 221 • ลงผิด 7 • ไม่รู้ 186 — ข้อมูล dev เป็นข้อมูลทดสอบ ใช้ดูหน้าตาเท่านั้น

ถ้าร้านบันทึกบัญชีมากขึ้นและลงสม่ำเสมอ แถบ "ลงถูก" จะยาวขึ้น ถ้าแถบ "ลงผิด" ยาวขึ้น แปลว่าเกณฑ์อาจหลวมเกินไป

> ฟิลด์ `coverage` (= predicted / total) และ `rate_accounts` (= hit_accounts / predicted) ยังอยู่ใน API สำหรับนักพัฒนาและตารางในแท็บผู้ดูแลระบบ

## 5. การทดสอบโดยผู้ใช้

### ตรวจสมอง
- ใช้ตรรกะเดียวกับการจำลองย้อนหลัง
- ข้อที่สมองตอบตรงกับที่บันทึกไว้ ระบบนับเป็นถูกให้อัตโนมัติ
- ผู้ใช้ต้องดูเฉพาะข้อที่สมองคิดต่างจากที่บันทึกไว้ หรือข้อที่สมองตอบไม่ได้

| กรณี | ตัวเลือก | ผล |
|---|---|---|
| สมองคิดต่าง | ที่บันทึกไว้จริงถูก | นับว่าสมองตอบผิด ใช้เป็นข้อมูลปรับสมอง |
| | สมองถูก | รายการนี้ไปอยู่ใน "รายการที่บันทึกเดิมอาจผิด" ให้นักบัญชีตรวจเอง (ระบบไม่แก้ให้) |
| | ถูกทั้งสองแบบ | นับว่าสมองตอบถูก รายการลักษณะนี้ลงบัญชีได้มากกว่าหนึ่งแบบ |
| สมองตอบไม่ได้ | สมองควรตอบได้ | เกณฑ์อาจเข้มเกินไป |
| | ไม่ตอบก็ถูกแล้ว | ยืนยันว่ารายการลักษณะนี้ควรให้คนตัดสินเอง |

### ถามสมอง
- ผู้ใช้กรอกอย่างน้อยหนึ่งอย่าง: คู่ค้า, เลขผู้เสียภาษี, คำอธิบาย หรือประเภทเอกสาร
- สมองตอบจากรูปแบบที่จำไว้ ณ ปัจจุบัน
- ถ้าใส่ยอดเงินด้วย ระบบจะคำนวณยอดแต่ละบรรทัดจากสัดส่วนเดิม

### การเก็บผล
- เก็บใน **MongoDB แยก** (container `shopbrain-mongo` บน 192.168.2.203) ไม่ใช่ Mongo หลัก
  - dev ใช้ฐานข้อมูล `shopbrain_dev` collection `brain_feedback`
- ตอนบันทึก server คำนวณคำทายใหม่เอง ไม่เชื่อค่าที่หน้าเว็บส่งมา
- ไม่เก็บ token และไม่เก็บอีเมล
- **ไม่แก้รายการบัญชีของร้าน**
- ถ้า Mongo แยกล่ม การทดสอบยังใช้ได้ แต่บันทึกผลไม่ได้ (ตอบ 503)

## 6. API

ทุก endpoint อยู่ใต้ `/billscan/api/v1` และเปิดให้เฉพาะ Owner ของร้าน

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| GET | `/shop-brain?shopid=` | สมองทั้งก้อน: รูปแบบ, ข้อมูลหลัก, ผลจำลองย้อนหลัง |
| GET | `/shop-brain/quiz?shopid=&days=&review=1` | ข้อถัดไปสำหรับตรวจสมอง พร้อมสถิติ |
| GET | `/shop-brain/parties?shopid=&q=` | ค้นหาคู่ค้าด้วยชื่อ รหัส หรือเลขผู้เสียภาษี |
| POST | `/shop-brain/ask?shopid=` | ถามสมอง |
| POST | `/shop-brain/feedback?shopid=` | บันทึกคำตัดสินของผู้ใช้ |
| GET | `/shop-brain/feedback/summary?shopid=` | สรุปผลการตัดสิน |

## 7. ค่าตั้งต้น (`DefaultOptions` ใน `build.go`)

| ค่า | ค่าเริ่ม | ความหมาย |
|---|---|---|
| `MinConsistency` | 0.6 | สัดส่วนขั้นต่ำของชั้น L1–L3 |
| `MinConsistencyFormat` | 0.9 | สัดส่วนขั้นต่ำของชั้น L4 |
| `WilsonZ` | 1.28 | ใช้ขอบล่างของความมั่นใจแทนสัดส่วนดิบ (0 = ใช้สัดส่วนดิบ) |
| `RecentAgree` | 2 | กี่ครั้งล่าสุดที่ต้องลงแบบเดียวกับแบบที่ใช้บ่อยที่สุด (0 = ไม่ตรวจ) |
| `StatementDirection` | true | Statement แยกกุญแจตามเงินเข้า/ออก |
| `HalfLifeDays` | 180 | น้ำหนักลดครึ่งทุก N วัน |
| `CheckedBoost` | 1.5 | ตัวคูณน้ำหนักของรายการที่ตรวจแล้ว |
| `MinJournals` | 100 | ร้านที่มีรายการน้อยกว่านี้จะขึ้นคำเตือนว่าข้อมูลยังไม่พอ |
| `MaxIdleDays` | 90 | ร้านที่ไม่มีรายการใหม่นานกว่านี้จะขึ้นคำเตือน |
| Cache TTL | 10 นาที | ระยะเวลาเก็บผลสมองในหน่วยความจำ (`service.go`) |

## 8. ข้อจำกัดปัจจุบัน

- สมอง**ยังไม่ได้ใช้ลงบัญชีจริง** มีไว้ให้ดูและทดสอบเท่านั้น
- คำตัดสินของผู้ใช้**ถูกเก็บไว้เท่านั้น ยังไม่ได้นำไปปรับเกณฑ์อัตโนมัติ** ต้องรอให้มีข้อมูลมากพอ แล้วจึงวิเคราะห์ว่าเกณฑ์ 60% / 90% เข้มหรือหลวมเกินไป
- billscan dev อ่านจาก `smldevdb` ซึ่งไม่ใช่ข้อมูลจริงของ prod ตัวเลขความแม่นที่ใช้ตัดสินใจควรวัดบน prod
- ไม่รู้ว่าใครเป็นคนกดตัดสิน เพราะไม่ได้เก็บตัวตนผู้ใช้ ถ้าร้านมีเจ้าของหลายคน จะแยกผลรายคนไม่ได้
- ยังไม่ได้ใช้ข้อมูลจากรูปบิล (OCR) เพราะต้องการควบคุมค่าใช้จ่าย

## 9. Roadmap

ข้อมูล ณ 2026-11-23 ตั้งแต่ระยะ 2 เป็นต้นไปเป็น**ข้อเสนอ** ยังไม่ได้ตกลงหรือเริ่มทำ

### ✅ ทำเสร็จแล้ว
- สมองร้าน v1 ใน billscan: กุญแจ 4 ชั้น, เกณฑ์ความสม่ำเสมอ และการจำลองย้อนหลัง
- หน้า `/shop-brain` มีแผนที่สมอง 3D, ตรวจสมอง, ถามสมอง และข้อมูลละเอียด ส่วนรายการบัญชีเปิดดูผ่าน dialog เดิมของระบบ

### ระยะ 0: ปิดงานรอบแรก
1. ทดสอบบน dev
2. commit bcaccount และเอกสารนี้
3. deploy Firebase dev
4. ต่อ billscan-prod เข้ากับ Mongo แยก (`BRAIN_MONGO_DB=shopbrain_prod`) แล้ว deploy prod
5. deploy Firebase prod

### ระยะ 1: วัดผลจริงบน prod (ประมาณ 2–4 สัปดาห์ ขึ้นกับจำนวนคนช่วยตรวจ)
- ให้เจ้าของร้านจริงหลายร้านช่วย "ตรวจสมอง" ร้านละอย่างน้อยหลักสิบข้อ
- **ปรับเกณฑ์ 60% / 90% จากคำตัดสินจริง**
  - ถ้า "สมองควรตอบได้" มีเยอะ แปลว่าเกณฑ์เข้มเกินไป
  - ถ้า "ที่บันทึกไว้จริงถูก" มีเยอะ แปลว่าเกณฑ์หลวมเกินไป
- **แก้จุดอ่อนที่พบแล้ว:** คำอธิบายกำกวมที่ไม่บอกว่าเงินเข้าหรือออก เช่น "ธนาคารกรุงเทพ transfer" ซึ่งในร้านตัวอย่างลงกลับด้านกัน 7 จาก 26 ครั้ง แนวทางคือเพิ่มทิศทางเงิน (เข้า/ออก) เข้าไปในกุญแจ แต่ต้องพิสูจน์ด้วยการจำลองย้อนหลังก่อนว่าดีขึ้นจริง
- ทำ backup รายวันให้ Mongo แยก (ตอนนี้ยังไม่มี)

### ระยะ 2: โหมดเงา (Shadow mode)
- ทุกครั้งที่บันทึกรายการบัญชีจริง ให้สมองทายเงียบ ๆ แล้วเก็บผลไว้เทียบกับที่บันทึกจริง ผู้ใช้ไม่เห็นอะไร
- ได้ตัวเลขความแม่นจากงานจริงทุกวัน โดยไม่ต้องพึ่งคนช่วยตรวจ
- ต้องเปลี่ยนให้สมอง**เรียนเพิ่มทีละรายการ** แทนการสร้างใหม่ทั้งก้อนทุก 10 นาที (ตรรกะ `predictor.learn` มีอยู่แล้ว)
- ยังไม่ใช้ AI จึงไม่มีค่าใช้จ่ายเพิ่ม

### ระยะ 3: ต่อกับ OCR (เริ่มมีค่าใช้จ่าย)
- OCR อ่านบิล → ได้เลขผู้เสียภาษี คู่ค้า และยอด → **สมองเสนอการลงบัญชี** แทน template ที่เขียนเอง
- ถ้าสมองตอบว่า "ไม่รู้" ให้กลับไปใช้ template เดิม หรือให้คนลงเอง
- ทุกข้อเสนอต้องให้คนกดยืนยันก่อนบันทึก
- **ต้องตัดสินใจเรื่องงบ:** การอ่านรูปบิลมีค่า OCR/AI ต่อรูป

### ระยะ 4: เปิดใช้จริงทีละร้าน
- เปิดเฉพาะร้านที่ผลจากโหมดเงาผ่านเกณฑ์ที่ตกลงกัน (เช่น ถูก ≥ 95% บนรายการที่สมองตอบ)
- มีสวิตช์เปิด/ปิดรายร้าน เมื่อสมองแม่นพอแล้วจึงค่อย ๆ เลิกใช้ template

### เรื่องที่ต้องตัดสินใจระหว่างทาง
- เกณฑ์ความแม่นขั้นต่ำก่อนเปิดใช้จริง (ระยะ 4)
- งบสำหรับอ่านรูปบิล (ระยะ 3)
- ร้านนำร่อง

> ข้อแนะนำ: ทำระยะ 1–2 ให้เสร็จก่อนตัดสินใจเรื่องงบของระยะ 3 เพราะสองระยะนี้ไม่มีค่า AI และจะตอบได้ว่าสมองที่ใช้แค่ข้อมูล GL แม่นพอหรือยัง
